# Runtime Uncertainty Signal Capture Design

## Background

Phase 0 has pivoted from provider-native `reasoning_tokens` to observable runtime uncertainty signals. Under the current Qwen3-VL-8B-Instruct + vLLM serving setup, provider-native `reasoning_tokens` is not available as a usable runtime signal. The new goal is to design signal capture that can later support step-level Fast/Slow routing without implementing `runtime_signal`, changing prompts, changing parsers, or running pilots in Task 3B.

Current constraints from Task 3A:

- The active `agentProfile` is `default`, which uses native tool calling.
- `parse_action()` receives `tool_call.arguments` as a dict, not full assistant text.
- Outer `trace_*.jsonl` contains token usage, latency, action summary, and observation, but not full raw model output.
- Inner `trace.jsonl` contains richer `model_snapshot` fields such as `raw_content`, `tool_calls`, `assistant_message`, and `parsed_action`.
- Future pilots must call `resolve_config_env_vars(load_config(path))`, not `load_config(path)` alone.
- U2 tasks must be skipped by default and require runner-layer allow gates.

## Signal Classes

### Model Self-Report Signals

Self-report signals are generated by the model and should be treated as claims, not ground truth.

- `confidence`: self-reported belief in the next action or current plan; not a calibrated probability unless later analysis proves calibration.
- `need_slow_planner`: model request for S2 planner/verifier/reflector help.
- `uncertainty_reason`: short categorical or free-text reason, such as ambiguous UI state, missing target, risky operation, or insufficient observation.

### Static Task Risk

Static task risk is assigned before execution from dataset metadata or a deterministic classifier. It applies to the whole task.

- `task_risk_level`: task-level risk bucket, separate from step risk.
- Examples: benign navigation, data lookup, external message/send, account or payment surface, irreversible device setting.

### Dynamic Step/Action Risk

Dynamic risk is computed per step from the parsed action, current app, and current observation.

- `step_predicted_risk_level`: model-predicted or planner-predicted step risk.
- `rule_based_step_risk_level`: deterministic risk bucket from action type and app context.
- `action_type_risk`: risk derived from tap/type/send/back/home/system-action categories.
- `app_sensitive_action`: whether the action occurs in or targets a sensitive app or screen.

`task_risk_level`, `step_predicted_risk_level`, and `rule_based_step_risk_level` must not be collapsed into one field. They answer different questions and should be analyzed separately before combined trigger-policy analysis.

### Execution Anomaly Signals

Execution anomaly signals are derived from runtime state transitions and trace observations.

- `repeated_action`: same or near-same action repeated in similar state.
- `stagnation_count`: number of steps without meaningful observed progress.
- `foreground_app_mismatch`: expected app differs from observed foreground app.
- `post_action_no_observable_change`: action produced no visible state change.
- `action_parse_failure`: action could not be parsed or validated.
- `execution_error`: tool, device, transport, or runtime error.

These can be trigger features, but any field used as a trigger must not also be used as the outcome label in predictive claims.

### Trace-Grounded Step Outcome Proxies

Outcome proxies are labels or weak labels for whether a step advanced execution. They must be stored separately from trigger features.

Recommended shape:

```json
{
  "trigger_features": {
    "self_report": {},
    "risk": {},
    "execution_state": {}
  },
  "outcome_proxies": {
    "execution_error": false,
    "action_parse_failure": false,
    "post_action_no_observable_change": false,
    "judge_derived_not_advanced": null
  }
}
```

`post_action_no_observable_change` is a rule-based proxy. `judge_derived_not_advanced` is judge-derived and must be labeled separately from rule-based proxies.

### Verifier-Generated Signals

Verifier-generated signals should be produced by a later S2/verifier path, not by the S1 action parser.

- `verifier_confidence`: verifier belief that the step advanced the task.
- `verifier_detected_issue`: categorical issue such as wrong app, wrong target, stalled, unsafe send, or insufficient evidence.
- `verifier_recommendation`: continue fast, retry, slow plan, ask user, or abort.

These are not required for the first capture path, but the trace schema should leave room for them.

## Option A: Assistant-Text Tagged JSON

Example:

```text
<runtime_signal>{"confidence": 0.72, "need_slow_planner": false}</runtime_signal>
```

### Parser Safety

In the `default` native tool-calling profile, assistant text is not the direct input to `parse_action()` for action extraction. That reduces parser collision risk, but does not eliminate profile-specific risk because traces and adapters may still preserve assistant content differently.

For text profiles such as `qwen3vl`, assistant text may contain `<tool_call>` markup that is parsed directly. In that mode, placing `<runtime_signal>` before or near `<tool_call>` can corrupt parser assumptions unless smoke tests prove otherwise.

### Native Tool-Calling Compatibility

Compatibility is uncertain. Some models and adapters may emit native tool calls with little or no assistant text. If the signal is only in assistant text, it may be absent in successful native tool-call turns.

### Qwen3VL Text-Profile Compatibility

This option is plausible for `qwen3vl` text-profile experiments because the signal can be emitted in the same text stream as `<tool_call>`. It requires explicit A/B/C smoke tests:

- signal before `<tool_call>`
- signal after `<tool_call>`
- no signal

### Outer Trace Availability

Outer `trace_*.jsonl` should not be assumed to contain the complete raw assistant text. Option A cannot rely on outer trace alone.

### Inner Trace Availability

Inner `trace.jsonl` may preserve `raw_content` and `assistant_message`, so it is the likely source for extracting tagged JSON if this option is tested.

### Implementation Complexity

Low for prompt changes, but medium for safe extraction and profile-aware validation. Task 3B does not implement it.

### Failure Modes

- Signal omitted when native tool calling suppresses assistant text.
- Malformed JSON.
- Signal text interferes with text-profile `<tool_call>` parsing.
- Signal appears after tool call and is truncated or not captured.
- Model learns to over-report confidence.

### Smoke-Test Requirements

Minimum U0 smoke tests must verify:

- The action still parses and executes.
- Tagged JSON is present in inner trace when expected.
- Tagged JSON does not appear inside tool-call arguments by accident.
- Both malformed and missing signal cases are handled without task failure.

## Option B: Runtime Signal Inside Native Tool Call Arguments

Example shape:

```json
{
  "action": "tap",
  "x": 120,
  "y": 440,
  "runtime_signal": {
    "confidence": 0.72,
    "need_slow_planner": false
  }
}
```

### Parser Safety

This is risky. `parse_action()` receives `tool_call.arguments` as the action input in the default native tool-calling profile. Adding signal fields to the action schema may pollute or invalidate action parsing.

### Native Tool-Calling Compatibility

Native tool calling can represent this shape, but compatibility with the current action schema is the concern. Tool schemas are contracts; adding non-action metadata to action arguments mixes control metadata with execution intent.

### Qwen3VL Text-Profile Compatibility

In text profiles, this would place the signal inside `<tool_call>` JSON. That can work syntactically only if the parser and schema tolerate the extra field, which should not be assumed.

### Outer Trace Availability

Outer traces preserve action summaries and parsed actions, so some signal fields might leak into outer traces if accepted. That is not a benefit because it couples signal capture to action execution.

### Inner Trace Availability

Inner traces would likely preserve the signal inside `tool_calls` and `parsed_action`, but again this is because the signal polluted action input.

### Implementation Complexity

Low to prompt, high to make safe. It would require schema, parser, validation, and possibly downstream tool changes, which are explicitly outside Task 3B.

### Failure Modes

- Action parser rejects unknown fields.
- Tool executor receives non-action metadata.
- Signal values become part of action replay or summaries.
- Future schema validation changes break signal capture.
- Predictive analysis becomes entangled with parser acceptance.

### Smoke-Test Requirements

This option would require strict parser and tool-executor smoke tests before any pilot. Given the risk, those tests should only be considered if no side-channel path is viable.

## Option C: Side-Channel / Model Snapshot / Trace-Layer Capture

Option C captures or derives uncertainty signals without changing action parser input. The signal is either recorded alongside the model snapshot or derived after the step from existing trace fields.

### Parser Safety

This is the safest option for the default native tool-calling profile because action parsing continues to receive only the normal tool-call arguments. Signal capture does not mutate the action schema.

### Native Tool-Calling Compatibility

This option fits native tool calling. It can use `tool_calls`, `assistant_message`, `raw_content`, token usage, latency, parsed action, and observations from trace snapshots without requiring the model to place metadata inside action arguments.

### Qwen3VL Text-Profile Compatibility

This option can also work for text profiles if the inner trace preserves `raw_content` and parsed action. If text-profile experiments need model self-report, Option A may be used as a profile-specific fallback after smoke tests.

### Outer Trace Availability

Outer traces provide token usage, duration, chat latency, time to first token, action, observation, and action summary. They are useful for latency and execution-state features, but insufficient for raw self-report extraction.

### Inner Trace Availability

Inner traces provide `raw_content`, `assistant_message`, `tool_calls`, `parsed_action`, and richer model snapshots. Task 4 must align inner and outer traces by step index, execution order, and session path.

### Implementation Complexity

Medium. It requires clear trace alignment and a schema for side-channel signal records, but it avoids action parser changes.

### Failure Modes

- Inner and outer traces fail to align.
- `raw_content` is missing in native tool-call-only turns.
- Derived signals are mistaken for model self-report.
- Trace-only extraction lags behind runtime and cannot trigger a live controller until later integration.

### Smoke-Test Requirements

Minimum U0 smoke tests must verify:

- A native tool-call step still executes unchanged.
- Outer and inner trace records can be matched for the same step.
- The captured signal record can be written without entering `parse_action()` input.
- Missing self-report fields degrade to `null` or absent fields, not parser or runner failure.

## Recommendation

Default for the native tool-calling profile: **Option C, side-channel / model_snapshot / trace-layer capture**. It preserves the current action parser contract and makes trace-grounded analysis possible without schema pollution.

Fallback for `qwen3vl` text profile: **Option A, assistant-text tagged JSON**, but only after U0 smoke tests compare signal placement before `<tool_call>`, after `<tool_call>`, and no signal. Option A should rely on inner trace extraction, not outer trace assumptions.

Not recommended: **Option B**, because it mixes runtime uncertainty metadata into native action arguments and is likely to pollute the action schema.

## Minimum U0 Smoke Test Before Any Pilot

Before any pilot collection:

- Run only U0-safe tasks.
- Use `resolve_config_env_vars(load_config(path))`.
- Confirm normal native tool calling still produces valid actions.
- Confirm `parse_action()` input remains the normal tool-call arguments dict.
- Confirm inner trace contains the expected snapshot fields for each step.
- Confirm outer trace contains token usage, latency, action summary, and observation.
- Confirm outer-inner trace alignment works by step index, order, and session path.
- Confirm signal extraction failure is non-fatal and recorded as missing/invalid signal.

## Trace Fields Required for Task 4

Task 4 should collect or align:

- session path
- task id
- step index
- outer trace event order
- inner trace event order
- token usage
- duration
- chat latency
- time to first token
- parsed action
- action summary
- observation summary or observation reference
- `raw_content`
- `assistant_message`
- `tool_calls`
- `parsed_action`
- model self-report signal record, if present
- rule-based risk signal record
- anomaly signal record
- outcome proxy record

Raw model output and raw observations should remain local uncommitted artifacts.

## Avoiding Circular Reasoning

Trigger features and outcome proxies must be separated in storage and analysis. A field used to trigger slow routing cannot be reused as the label proving that the trigger predicts failure.

Allowed trigger features:

- self-report confidence
- need slow planner
- static task risk
- dynamic step/action risk
- repeated action
- stagnation count
- foreground app mismatch

Outcome proxies:

- execution error
- action parse failure
- post-action no observable change
- judge-derived not advanced

When analyzing predictive value, compare trigger features against outcome proxies from a different source or layer whenever possible.

## U2 Safety Requirements for Later Pilot Runner

U2 tasks must be skipped by default. Prompt-only safety is insufficient; enforcement must be in the runner.

Required future controls:

- `--allow-u2`
- `--dry-run-u2`
- `--allowed-contact`
- `--message-prefix`
- `--allow-task-id`

Default behavior must skip U2 unless explicitly enabled. Real U2 execution must also constrain contacts, prepend safe message text where applicable, and allow only explicitly named task ids.

## Task 3B Non-Goals

This design does not:

- implement `runtime_signal`
- modify GUI prompts
- modify the action parser
- modify model adapters
- modify eval runners
- modify trace code
- run pilots
- run U2 tasks
- implement the Fast/Slow Controller
